## 2. ACHADOS QUALITATIVOS
----------------------------------------------------------------------------------------------------
(a) GNN_PostBase vs. base congelada -- evidencia PARCIAL de refinamento.
    Unica comparacao em escala igual disponivel (mesma base, mesma metrica mse):
      FNO2d/run_0001 sozinho             -> best_test = 0.028952
      GNN_PostBase/run_0001 (sobre ele)  -> best_test = 0.025866   (-10.7%)
    Isso sugere que o GNN de fato refina o campo do FNO congelado nesse caso -- contraria
    parcialmente a suspeita registrada no CLAUDE.md (pendencia: "erro medio do FNO menor que
    o do GNN do GNN_PostBase treinado em cima dele").
    PORTANTO as demais 6 runs de GNN_PostBase usam como base o FNO2d/run_0002, que foi treinado
    com loss relative_l2 -- o test_loss dessa base fica em outra escala (~0.35) e NAO e comparavel
    ao mse do GNN (~0.03-0.19) nessas runs. A duvida do CLAUDE.md so fica resolvida de fato
    reavaliando a base congelada sob a MESMA metrica (mse) usada pelo GNN.

(b) FNO_GNN / GNN_PostBase custam 2-3x mais tempo de parede que FNO2d para o mesmo numero de
    epocas (ex.: 500 epocas ~= 70 min em FNO2d vs. ~= 150-240 min em FNO_GNN/GNN_PostBase no
    dataset atual), apesar de contagens de parametros proximas (~5.3M em ambos). O overhead
    vem do processamento de grafo (mensagens por no/aresta), nao do tamanho do modelo.

(c) motor_phase_0 nao e comparavel em dificuldade. Os menores test_loss registrados no
    levantamento (0.0067, 0.0042) vem desse dataset inicial (fase do rotor fixa, geometria
    mais restrita), nao do dataset atual -- refletem uma tarefa mais facil, nao um modelo
    superior.

(d) Uma run divergiu claramente: FNO2d com 37.6M parametros
    (motor_fixed_geometry_135x270/FNO2d/run_0011, conv_width=16) atingiu test_loss=1.52 e foi
    interrompida -- modelo grande demais / instavel para essa configuracao.

(e) loss_cfg (tail_alpha, tail_k_frac, subtract_fno) so aparece no dataset atual
    (motor_default_v4_135x270) -- e a implementacao em andamento do item pendente no CLAUDE.md
    sobre "losses focadas em erro percentual (media/p95)":
      - tail_alpha/tail_k_frac: termo de cauda top-k opcional somado a MSE (tail_alpha=0 desliga)
      - subtract_fno: em FNO_GNN/GNN_PostBase, faz o GNN aprender o RESIDUO (delta) sobre a saida
        do FNO em vez do campo absoluto
    Comparacoes preliminares dentro do dataset atual (GNN_PostBase, base=FNO2d/run_0002, loss=mse):
      subtract_fno=False (run_0003, 500 ep) -> best=0.03342
      subtract_fno=True  (run_0005, 420 ep, interrompida) -> best=0.03255  (levemente melhor)
    Com loss=mae, o quadro inverte:
      subtract_fno=False (run_0006, gnn_layers=2, 410 ep, interrompida) -> best=0.08788
      subtract_fno=True  (run_0007, gnn_layers=2, 450 ep, interrompida) -> best=0.18618  (bem pior)
    Nenhuma dessas runs rodou ate o fim (todas "stopped") -- tratar como indicio, nao conclusao.

## 5. NOTAS METODOLOGICAS
----------------------------------------------------------------------------------------------------
- best_test = menor test_loss ja atingido pelo checkpoint "best" durante a run (nao e
  necessariamente o valor final).
- epocas = numero real de epocas treinadas (pode exceder n_epochs configurado quando a run foi
  retomada / resumed).
- tempo(min) = estimativa: media de (train_time_s + eval_time_s) dos pontos logados (a cada 10
  epocas) * numero de epocas reais, convertido para minutos. Aproximado, nao um cronometro exato.
- Valores de loss NAO sao comparaveis entre linhas com "loss" diferente (mse vs relative_l2 vs
  mae tem escalas diferentes).
- Fonte dos dados: data/logs/<dataset>/<arch>/run_XXXX/{config.json, metrics.jsonl, status.txt}
